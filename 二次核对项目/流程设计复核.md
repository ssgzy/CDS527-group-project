## 结论先行

- **整体流程设计合理。**
- **核心实验链条不是胡乱试模型，而是有明确控制变量设计。**
- 但如果按作业文字最严格解释，当前实现仍有一个需要说明的缺口：
  - “为不同模型调超参数并报告最佳分数”这一条，项目里主要落实在 `Section 4` 的 `LR + class weights + regParam sweep`
  - 并没有对 `Section 2` 里的每个模型逐一系统调参

## 哪些地方是合理的

### 1. 先做 baseline，再做对照实验

- 这是标准流程。
- baseline 先给出一个低门槛但可解释的参照点，后面所有改进才有比较基础。

### 2. 把“模型差异”和“特征差异”拆开做

- 这是当前项目最合理的地方之一。
- 它避免了“模型和特征同时变，最后不知道是谁起作用”的混淆。

### 3. 在严重不平衡数据上把 macro-F1 作为主指标

- 这是合理的。
- 从结果看也确实验证了这个选择：accuracy 在多个阶段都会误导。

### 4. 把改进重点放到类别不平衡处理上

- 这不是拍脑袋操作，而是由 `Section 1` 和 `Section 3` 的结果推出来的。
- `Section 3` 里 BOW 系列方法都卡在 `0.2337`，说明真正卡点不在特征微调，而在类别不平衡。

## 哪些地方需要更严谨地解释

### 1. 作业要求中的“统一 split / metric”

- 项目当前口径是：
  - `stratified 80/20`
  - `seed = 42`
  - 主指标 `macro-F1`
- 这套协议在项目内部保持一致，**所以执行上是规范的**。
- 但作业说明原文写的是老师会给 standardized split / evaluation metric。
- 当前仓库中看不到老师明确给出的 split 索引或 metric 定义，因此要在 report / oral 中说成：
  - “project adopted a fixed team-defined protocol and used it consistently throughout”
- 不要说成“老师指定了这套 split 和 metric”，除非你们另有外部确认记录。

### 2. “Fine-tune different hyper-parameter for each model”

- 现在的实现并不等于“每个模型都调参过”。
- 实际做的是：
  - baseline 固定
  - model comparison 用默认或轻量设置比较
  - improvement 阶段重点调 `LR + class weights`
- 这仍然是合理的研究推进方式，但对外表达不能夸大。

### 3. Section 3B 未做 GloVe / BERT

- 这不是错误。
- 但最好明确写成：
  - 因为项目要求以 PySpark 原生主线为主，且时间与环境受限，所以将 GloVe / BERT 作为 future work，而非正式实验矩阵
